# Administrador inicial: diagnóstico y procedimiento explícito

**Estado: procedimiento preparado; ninguna inserción ni cambio de contraseña ejecutados.** La creación requiere aprobación previa y solo sirve si no existe el usuario ni ninguna asignación de ADMINISTRADOR.

## Diagnóstico real de solo lectura

Conexión comprobada: esart_db, cuenta esart_aplicacion. El esquema actual ya incluye las columnas de seguridad y esart.sesiones_usuario. No se ejecutó Alembic ni DDL.

- Tabla de usuarios: **esart_ref.usuarios**, PK BIGINT con identidad; hay **1 usuario**.
- Usuario propuesto por la configuración existente: **admin.esart**, **ya existe**, id 1, activo, con hash de formato bcrypt y sin cambio obligatorio de contraseña.
- Rol: **esart.roles**, id **1**, código **ADMINISTRADOR**, nombre Administrador, activo; está definido y permitido por el CHECK de roles.
- Hay **1 asignación de administrador** mediante esart.usuario_roles. Por ello **no procede crear otro primer administrador** ni actualizar el existente con este comando.
- La cuenta operativa tiene SELECT/INSERT en usuarios y usuario_roles, lectura del rol y USAGE de la secuencia de usuarios. Dispone de UPDATE sobre la columna ultimo_acceso_en, aunque no de UPDATE general sobre usuarios: el login puede registrar ese dato sin exigir ampliar permisos globales. Sesiones tiene los permisos observados para su flujo actual.

El inventario de columnas, restricciones, índices y permisos está en [ESART_ADMINISTRADOR_DIAGNOSTICO.json](ESART_ADMINISTRADOR_DIAGNOSTICO.json). No contiene hashes ni contraseñas. La forma válida del hash no demuestra que corresponda a la contraseña que posee el operador.

## Campos y relaciones

El índice único uq_esart_usuario_nombre_ci compara **lower(usuario)**; la búsqueda usa la misma normalización. La FK de roles restringe su eliminación. El administrador hereda las concesiones ya definidas en rol_permisos/componentes; no se agregan ni modifican permisos, componentes, roles o excepciones individuales. Tener el rol no es un bypass de autorización.

## Hash y login existentes

`aplicacion/seguridad/contrasenas.py` es el mecanismo reutilizado: bcrypt directo con sal aleatoria, costo 12 y límite de 72 bytes UTF-8. El comando rechaza vacío y exceso en bytes, confirma la entrada y usa generar_hash_contrasena/verificar_contrasena. No usa el valor ADMIN_HASH_CONTRASENA para el alta explícita ni muestra el hash. No modifica .env.

POST /api/auth/login llama a servicios/autenticacion.iniciar_sesion: busca por nombre sin distinguir mayúsculas, verifica bcrypt, exige usuario activo y rol activo, crea una fila de sesión, actualiza último acceso y emite JWT en cookie HttpOnly. Contraseña incorrecta, usuario inexistente/inactivo o ausencia de rol producen el mismo 401 genérico. El 401 observado **no prueba ausencia del administrador**, pues ya existe y está activo.

Se detectó una creación automática desde .env en el ciclo de arranque de FastAPI. Se retiró esa invocación: **arrancar la API ya no crea usuarios ni roles**. El helper anterior asegurar_administrador_inicial se conserva como código legado, pero no es el procedimiento recomendado: podía crear un rol ausente y utilizar el hash del entorno. No invocarlo para esta tarea ni usar initial_data.py.

```powershell
.venv/Scripts/python.exe -m herramientas.crear_administrador_inicial --usuario admin.esart
```

Este plan ya se ejecutó en modo de lectura y confirmó usuario existente y administrador asignado. El nombre no es una credencial predeterminada nueva: procede de la configuración y corresponde a una cuenta existente. Para otra instalación usar el nombre expresamente aprobado, sin asumir este valor.

Para comprobar localmente la contraseña que ya posee el operador, sin crear sesión ni modificar la cuenta:

```powershell
.venv/Scripts/python.exe -m herramientas.crear_administrador_inicial --usuario admin.esart --verificar-contrasena
```

La clave se introduce exclusivamente en terminal mediante getpass, sin eco. El comando rechaza fallback visible; no usar tuberías, argumentos de contraseña, redirecciones ni grabaciones de terminal. El resultado solo informa coincidencia y estado, no la clave/hash. Esta comparación no se ejecutó desde Codex porque la contraseña permanece con el operador.

Solo para una instalación sin el usuario y **sin ningún administrador asignado**, después de presentar el plan y obtener aprobación específica:

```powershell

```

NOMBRE_APROBADO es un marcador que debe sustituirse. **No ejecutar esta alta en la instalación actual:** se detendrá porque el administrador ya existe. No cambiar el nombre para eludir esa comprobación.

## Garantías y transacción

- Por defecto es solo lectura. --aplicar es explícito y no se usó en esta tarea.
- No acepta contraseña por CLI/archivo/env; usa getpass con confirmación, genera y verifica el hash en memoria. Las referencias a la clave se descartan tras usarlas; Python no garantiza borrado físico de memoria.
- Revisa de nuevo nombre, rol y asignaciones tras la entrada interactiva. Usa bloqueo asesor transaccional para ejecuciones de este comando y transacción SERIALIZABLE; UNIQUE protege el nombre frente a altas concurrentes. Ante conflicto de integridad/serialización, falla sin reintentos que cambien otras cuentas.
- Inserta exclusivamente una fila de usuarios y una de usuario_roles. No crea ni activa roles ni modifica otros usuarios. Verifica el rol asignado antes del COMMIT externo; cualquier excepción revierte ambas filas.
- Repetir no restablece claves ni reactiva usuarios: rechaza la operación. No se usa un UPSERT ni se actualizan fechas existentes.
- No cambia la estructura, permisos SQL, historial Alembic, catálogos o unidades militares. Una transacción fallida puede consumir un valor de identidad: PostgreSQL no revierte secuencias y no se reajustan.
- Errores conocidos muestran mensajes sin secretos; errores del controlador muestran únicamente su tipo, sin SQL/parámetros. No ejecutar con eco SQL o depuradores que capturen variables locales.

## Validación posterior y decisión pendiente

La compatibilidad del mecanismo de hash y los campos se comprueba con código y metadatos; **no se afirma un login exitoso del usuario real** sin probar su clave. La comparación local de contraseña es el siguiente paso no destructivo. Si coincide, comprobar el endpoint real desde el formulario Angular o un cliente que no guarde la contraseña; debe responder 200 y entregar la cookie HttpOnly, sin token en JSON.

Un login exitoso **escribe** sesión y último acceso. No se llamó al endpoint durante este diagnóstico. La prueba real posterior debe acordarse explícitamente; no usar credenciales ficticias ni sustituir dependencias de autenticación para simular éxito. Si la contraseña no coincide, cualquier recuperación/cambio del usuario existente es un procedimiento distinto que requiere autorización específica; este comando no lo implementa.

Antes de autorizar un alta futura, revisar el plan con nombre aprobado, rol ADMINISTRADOR ya definido/activo y ausencia de administrador. Para este caso se solicita una decisión sobre la cuenta existente; no una autorización de inserción innecesaria.
